# dsh-team-conductor 的六个上游问题

**坐标来源：** 全部坐标读自本机 build 的只读副本 `work/ref/dsh/node_modules/@deepseek-ai/`（内核版本统一为 `0.2.0-rc.2`；未提取的包经 `work/asar-tool.mjs` / `work/asar-grep.mjs` 从 `app.asar` 内读取）。行号对应上述副本；`lib/index.js` 指的是包内该路径，不是插件自己的文件。凡是**没有**在本机源码里读到的结论，都在表内标注「需上游确认」并写出依据。

## 两条需要上游确认的判断

**问题 4 的「重复投递」是内核缺陷还是宿主行为。** 本插件能证明的是：notice source 不含 activation 标识，同一 Activation 二次通知在内容上不可区分（`continuation-messages.js:98-103`）。至于二次通知的确切触发条件（例如某个 disposal 路径重复进入、或 wake 重放），本机源码中没有一条可复现的调用链能单点归因，因此**不在本文件里断言触发路径**。需要上游确认的是：修在 source 标识层还是 `notifySettlement` 幂等层。

**问题 6 的修复位置。** 依据只有「检索无命中」与「bash 工具的成败不校验产物」，属于「缺少纪律文本」而非「某个函数写错」。因此标注需上游确认：这条纪律该由 `@deepseek-ai/dsh-tool-bash` 的文案、内核 `TEAM_POLICY` 段，还是通用系统提示承担。

## 本插件不做的两件事（边界）

1. **不改内核调度。** `team_overview` 的测量与等级只用于显示与建议；`compact` 是显式动作，只在 `team_member_edit action=compact` 时发生。
2. **不替换内核工具。** 六个工具都是新增名字（内核 team bundle 的 `spawn_teammate`/`send_message`/`list_agents`/`wait_agent`/`interrupt_agent`/`team_task_*` 与本插件的 `team_overview`/`team_member_edit`/`team_capacity_set`/`team_message`/`team_member_add`/`team_member_delete` 无重名），bundle patch 只做 `insert`，不含任何 `disabled: true`。

## 已知实现边界（坐标在本插件内）

**`team_member_delete` 的 `seal_kernel` 只在 `provisioning` 成员上可能成功，这是刻意的。** 内核投影只允许一次迁移（`provisioning → active|failed`），对任何其它起点抛 `teammate "<name>" has an invalid ${prior.phase} -> ${member.phase} transition`（`@deepseek-ai/dsh-experimental-agent-team/lib/types/projection.js:196-203`，`:128-133` 还会让 `TeamJournal.state()` 在 `projection.failure` 存在时抛错）。所以对已 `active` 的记录**追加 `phase:"failed"` 是非法的**：那会污染投影、让之后每次 `journal.state()` 读取都失败、把整支 Team 的编排面弄坏。实现因此从不尝试：`sealMemberInKernel()` 仅在 `phase === "provisioning"` 时追加，其余情况返回 `immutable-active` / `immutable-failed` 并**不写任何日志**。删除的实际效果来自三件事：编排层墓碑（`deleted`/`deletedAt`/`deleteReason`）、`agentTeams.sendMessage` 上的消息拦截、以及 `raiseCeiling(+1)`。

**`rename` / `reassign` 改的是编排层名字，不是内核名字。** 内核把 `name`/`provider`/`context` 当作不可变身份字段（`projection.js:196-201`，`changed immutable identity fields`），所以改名只写侧车 `alias` 并把旧名压进 `formerNames`；新旧名字都能被本插件寻址，但内核 `list_agents` 仍显示 durable name。这是设计约束，不是缺口。

**两个守卫都是进程内包装。** 结算守卫装在 `subagents.continuations.activations.notifySettlement`（激活注册表，不是 `subagents` 服务），按 Activation 对象身份去重；删除守卫装在 `agentTeams.sendMessage`（只覆盖走 Team 服务的投递——按 child session id 直达 `subagents.sendMessage` 的通道不在其覆盖面内），按侧车墓碑判定。都不跨进程，重启即恢复内核原样；分别可用 `dedupeSettlementNotices: false` / `blockDeletedTargets: false` 关闭。
